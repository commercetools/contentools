## D2. Transport: how the app calls the service

**Decision:** one `fetch`-compatible function, `forwardToFetch(url, init)`, built on `executeHttpClientRequest`, injected into each manager via
the puck `fetcher` prop (contract owned by J; K needs exactly this).

Alternatives rejected:
* `actions.forwardTo.*` via `useAsyncDispatch`: no `PUT` (SDK file lines 98-135), awkward for `FormData`, couples puck-api to Redux.
* `createApolloContextForProxyForwardTo` + `useMcQuery`: only for a GraphQL service; our service is REST.
* Direct browser -> service with a static token: token in a public JS bundle; needs service CORS; breaks the permission model; forbidden by Q-01a.
* Making puck-api depend on `@commercetools-frontend/*`: puck must stay usable outside the Merchant Center (playground, storefront preview).

```ts
// admin-app/src/hooks/use-service-fetcher/forward-to-fetcher.ts   (skeleton, completed in tasks.md 4.1)
import { buildApiUrl, executeHttpClientRequest } from '@commercetools-frontend/application-shell';

export type ServiceFetcher = (url: string, init?: RequestInit) => Promise<Response>;

export const forwardToFetch: ServiceFetcher = (url, init = {}) =>
  executeHttpClientRequest<Response>(
    async (options) => {
      const res = await fetch(buildApiUrl('/proxy/forward-to'), {
        ...options,                                   // credentials + MC headers (Accept, X-Project-Key, X-Correlation-Id, ...)
        method: init.method ?? 'GET',
        headers: { ...options.headers, ...(init.headers as Record<string, string> | undefined) },
        body: init.body,
      });
      return { data: res, statusCode: res.status, getHeader: (name) => res.headers.get(name) };
    },
    {
      forwardToConfig: {
        uri: url,                                     // the FULL service URL incl. path and query
        audiencePolicy: 'forward-url-origin',         // aud = service origin: one audience for all REST paths
        includeUserPermissions: true,                 // adds the `canView<Entry>`/`canManage<Entry>` claim
        version: 'v2',
      },
    }
  );
```
Facts this relies on (all verified, see explore.md section 3): `executeHttpClientRequest` returns `response.data` untouched (here the `Response`), only treats **401** specially (one retry with token renewal),
adds `X-Project-Key`, `X-Application-Id`, `X-Correlation-Id`, `Accept`; `buildApiUrl` prefixes the MC API origin derived from `cloudIdentifier`.
Consequences:
* `Accept: application/json` is set by the shell; the puck `httpClient` sets `Content-Type` itself; for `FormData` it sets none (browser adds the boundary) - unchanged.
* The `audiencePolicy` choice is a cross-spec contract: **E must configure `createSessionMiddleware({ audience: <service origin>, audiencePolicy: 'forward-url-origin', issuer: CLOUD_IDENTIFIER })`**.
  The sibling `search-config` uses `forward-url-full-path` because it has one `/graphql` path; with REST paths per business unit the audience would change per URL.
* The service must answer **403** (not 401) for "authenticated but not permitted", otherwise the shell retries needlessly.
* `X-Project-Key` is sent by the shell; the service MUST compare `req.session.projectKey` to its own `CTP_PROJECT_KEY` (otherwise a user of another project that has this custom application installed could use this service). Recorded in `questions.md` Q-K4 for E.
* Local dev needs an https tunnel because forward-to rejects `http` targets; see tasks.md group 8.
* Gateway behaviour for PUT / multipart / body size is not documented: verified live (manual.md M-K2) and the fallback is recorded as R2.

Where the URL comes from: `useApplicationContext((ctx) => ctx.environment.serviceUrl)`; `serviceUrl` is `additionalEnv` set by L from `CONTENTOOLS_SERVICE_URL`.
`ServiceProvider` trims trailing slashes, validates `https:`, memoizes `{ serviceUrl, fetcher }`, and renders `ServiceNotConfigured` otherwise
(local `http://localhost` is allowed only when `window.app.env === 'development'`? **No**: the gateway refuses it, so a non-https URL is always "not configured" with a hint to start a tunnel).

## D3. `routes.tsx`

```tsx
// admin-app/src/routes.tsx (final shape; tasks.md 4.3)
import { Switch, Route, Redirect, useRouteMatch } from 'react-router-dom';
import { ContentManager } from '@commercetools-labs/puck-content-manager';
import { PageManager } from '@commercetools-labs/puck-page-manager';
import { ThemeManager } from '@commercetools-labs/puck-theme-manager';
import { useApplicationContext } from '@commercetools-frontend/application-shell-connectors';
import { useBusinessUnit } from './contexts/business-unit';
import { useService } from './contexts/service';
import AdminLayout from './components/admin-layout';

const ApplicationRoutes = () => {
  const match = useRouteMatch();
  const dataLocale = useApplicationContext((ctx) => ctx.dataLocale ?? undefined);
  const { selectedBusinessUnitKey } = useBusinessUnit();
  const { serviceUrl, fetcher } = useService();
  const common = { baseURL: serviceUrl, businessUnitKey: selectedBusinessUnitKey, locale: dataLocale, fetcher };
  return (
    <AdminLayout>
      <Switch>
        <Route path={`${match.path}/pages`}><PageManager {...common} parentUrl={`${match.url}/pages`} /></Route>
        <Route path={`${match.path}/items`}><ContentManager {...common} parentUrl={`${match.url}/items`} /></Route>
        <Route path={`${match.path}/theme`}><ThemeManager {...common} /></Route>
        <Route exact path={match.path}><Redirect to={`${match.url}/pages`} /></Route>
      </Switch>
    </AdminLayout>
  );
};
```
Notes: (1) `parentUrl` keeps the leading slash (source used `match.url.slice(1)`; react-router normalizes both, but the slash version is what `BrowserRouter basename` documents).
(2) `key={selectedBusinessUnitKey}` is added on each manager so that a BU change remounts and refetches instead of showing stale lists.
(3) `locale`: puck uses it for catalogs (only `en`/`es` today) and product search; MC `dataLocale` is the right "content locale". `de` falls back to English inside puck until J/I add a German catalog (Q-K3).
(4) The `/theme` route has no router of its own in puck; it relies on the shell's router (`useHistory`), unchanged.
(5) No `projectKey`, no `jwtToken`.

## D9. Local development against unpublished puck packages

| Option | Verdict |
| --- | --- |
| Registry pre-release `1.0.0-rc.N` (tag `next`) | **Required for Connect builds** (Connect cannot resolve a workspace; M-08). Also the default for developers once rc exists |
| Tarballs (`yarn pack` per package in `puck/`, referenced from `resolutions` as `file:`) | **Chosen for the inner dev loop before/without a publish.** `yarn pack` (Yarn 4 in `puck/`) rewrites `workspace:^` to concrete versions, so `resolutions` must map **every** `@commercetools-labs/puck-*` to its tarball, otherwise a transitive dep is fetched from the registry (404 before first publish). Precedent: `search-config/tools/vendor-runtime-tarball.mjs` |
| `link:`/`file:../puck/packages/x` | Rejected: symlinks give duplicate React/Nimbus (R4) and need `preserveSymlinks`; `workspace:` ranges inside are unresolvable by Yarn 1 |
| `yalc` | Rejected: extra tool, `.yalc/` and `yalc.lock` churn, same duplicate-copies and cache issues, no gain over tarballs |

Mechanics (`tools/admin-app-use-local-puck.mjs`, tasks group 7): (1) `yarn --cwd puck build`; (2) `yarn --cwd puck workspaces foreach --all --no-private pack --out <abs>/admin-app/.local-puck/%s.tgz`;
(3) copy `admin-app/package.json` to `.local-puck/package.json.orig`; add `resolutions` for every tarball; (4) `yarn --cwd admin-app install --force --frozen-lockfile=false --no-lockfile`; (5) `--restore` copies the original back and runs `yarn install --frozen-lockfile`.
`.local-puck/` is git-ignored; `yarn verify` (via `check:pins`) and the root `gate` script grep `package.json` for `file:` (spec requirement). Re-running step 2-4 after every puck change is the loop (about 40 s); for tighter loops use the playground (`puck/playground`) which has HMR on workspace sources.
