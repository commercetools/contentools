# Questions raised by e-service-auth-model

| ID | Question | Recommended default (assumed) | Affects |
| -- | -------- | ----------------------------- | ------- |
| Q-E1 | Does a storefront need a *preview mode* (draft content) that cannot hold a server-side secret? Preview reads (`/:bu/preview/*`) are protected in this design (source: public with a project key). | Storefront preview runs server-side with `SERVICE_API_TOKEN`; no public preview. | E, F, J |
| Q-E2 | Should write access require a specific MC permission (`MC_REQUIRED_PERMISSION`, e.g. `canManageContentools`) or is "user has access to the project" enough? | Optional key, default unset (any user with access to the project). Spec L defines the permission group names; if the owner wants it enforced, set it at install. | E, K, L, H |
| Q-E3 | Rate limiting / caching for the public published reads (they call commercetools with service credentials for datasource resolution on every request). | Only the opt-in public resolve route is limited (global per-process window, design D-E10); published reads are not limited: document, recommend a CDN in front of the storefront-facing URL. | E, F, P |
| Q-E4 | `GET /:bu/media-library` and datasource/product-search reads were public in the source and are now protected. Any storefront consumer that needs them anonymously? | No (editor-only). | E, F, G |
| Q-E5 | `SERVICE_API_TOKEN` rotation: single token, rotate by redeploy. Support two tokens (current + next) for zero-downtime rotation? | No, single token. | E, H |
| Q-E6 | (from J's Q-J2) Should datasource resolve and product search be public read-only by default so the storefront renderer can show product blocks without `resolvedData`? | No. Published page reads already embed `resolvedData` server-side. Product search stays protected; built-in datasource resolve is opt-in via `PUBLIC_DATASOURCE_RESOLVE=true` with a global rate limit (design D-E10). If J wants the renderer to call resolve anonymously, set the flag at install. | E, F, J, H |
| Q-E7 | (from J's Q-J7) Error body shape: E/D contract is `{message, statusCode, correlationId, code?, errors?}`; `code` is optional and stable, clients key on the HTTP status first. Confirm. | Confirmed in D/E (optional `code`). | D, E, G, J |
